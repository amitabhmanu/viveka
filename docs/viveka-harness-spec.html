Viveka Harness Specification

How the framework in Evidence That Cuts Both Ways is built and run as a research harness: Claude Code builds and operates a deterministic, versioned pipeline, and every measurement comes from registered instruments whose outputs are archived and auditable.

Implements Evidence That Cuts Both Ways (revision of 14 September 2026) · companion to The Insulated Core
Harness principles6 clauses · every requirement below traces to one
H1

Engineer, not instrument

Claude Code writes, runs and maintains the pipeline. No label, measure or verdict is ever produced inside an agent session; they come only from versioned pipeline code and registered coders.

H2

Frozen before seen

Every threshold, rubric, prompt, query and event list is frozen by content hash before the data it governs is coded or scored. A change after freezing is a new registry version.

H3

Provenance on everything

Every artefact records the registry hash, code commit, inputs and coder that produced it. Raw coder output is archived before it is parsed.

H4

Instruments held to P

Coders pass the leakage test, the symmetry audit and the agreement threshold before their labels count. One model family is one coder.

H5

Deterministic core

The verdict procedure is a pure function of measures and registry, tested on synthetic data before it ever sees a real case.

H6

Revisions are debited

Every change to the codebook, prompts or parameters is appended to a change ledger with the result that prompted it. Nothing is edited silently.

1 · Scope

What the harness does, and what it does not

The harness turns the framework into a runnable study: it assembles corpora, builds the social and epistemic layers, codes evidence under the coder rules, computes the measures with their intervals, applies the four-gate verdict procedure, and checks the framework against its own revision triggers.

In scope

  • The pilot (fifth force against cold fusion), its reserve pair, and the calibration fields named in the framework.
  • Every instrument in the framework: the Anomaly Response Ledger (codes A–D, rounds), Δ read reason by reason, Ω, H, τ, χ, and the independent checks (depth ratio, deletion).
  • The registry, its freeze and versioning protocol, and the change ledger.
  • The coder subsystem: automated coders through batch APIs, human coders through exported packets, and the audits every coder must pass.
  • The simulator that sets m and v and checks whether the pilot can separate its cases at all.
  • Claude Code configuration: project instructions, permissions, hooks, subagents and skills.

Out of scope

  • A user interface beyond generated HTML reports.
  • Scoring contested cases (psychoanalysis, string theory and the rest). The harness supports them, but none is scored until calibration and the pilot have passed.
  • Acquiring any literature by circumventing paywalls, access controls or a source's terms.
  • Changing the framework. Where building exposes a gap in the framework, the harness records it as a decision for the framework document (§17), not a local workaround.

Normative language

must marks a requirement the build is checked against. decision marks a choice that belongs to the project owner and is listed in §17. Parameter values quoted here are the framework's proposed values; the registry, not this document, is authoritative once frozen.

Blocking gap: no Linux runtime

The framework requires community detection by at least two methods, one of them a hierarchical stochastic block model. The reference implementation, graph-tool, does not run natively on Windows; GROBID, used to extract citation contexts from PDFs, is distributed as a Java service normally run in Docker. Until a Linux runtime exists (WSL2, Docker Desktop, or a remote Linux runner), stage S3 can run Leiden clustering only, and every verdict computed without the second method must be marked provisional and cannot pass gate 4. Installing WSL2 changes system settings and is left to the project owner.

Credentials

  • ANTHROPIC_API_KEY for automated coders (§8).
  • An OpenAlex API key: required for all API calls since 13 February 2026, with usage-based credits. Bulk work uses the free CC0 snapshot instead (§14).
  • A Semantic Scholar API key, for citation contexts at a usable rate.
  • Credentials for the second model family, once chosen (decision D-2).

Credentials live in a git-ignored .env file loaded by the pipeline. Claude Code must be denied read access to it (§11).

3 · Architecture

Four layers, one direction of trust

The layers differ in what they may do. Orchestration may change code but produces no evidence. The pipeline produces evidence but cannot change the registry. The registry governs both and changes only through its versioning protocol.

Why the agent is not an instrument

A Claude Code session is not reproducible, reads the whole repository including the predictions, and has taken part in developing the framework. Any of those disqualifies it as a coder under the framework's own rules. Automated coding therefore runs through fixed prompts sent by pipeline code to a pinned model through the Message Batches API, with outputs archived; the agent builds that code but never stands in for it.

5 · Registry

Registry, freezing and versions

The registry is the framework's "fixed before scoring" made mechanical. The pipeline reads it; nothing writes to a frozen version.

Contents

Thresholds and conventions from the framework's parameter registry live in thresholds.yaml, each with its value, its status (fitted, simulated, convention) and, for fitted and simulated values, the run that produced it. Instrument components from the framework's second registry table live in the other directories. The loader must reject a registry with any parameter used by code but missing from the file.

# registry/thresholds.yaml (excerpt)
version: 3
parameters:
  l_lag_years:      {symbol: "ℓ", value: 2,    status: convention}
  interval_level:   {value: 0.95,              status: convention}
  w_window_years:   {symbol: "w", value: 5,    status: convention,
                     variants: {length: [4, 7], shift_max: 2}}
  o_overlap:        {symbol: "o", value: 0.3,  status: convention, sweep: [0.2, 0.5]}
  j_idle_years:     {symbol: "j", value: 10,   status: convention}
  kappa_min:        {symbol: "κ", value: 0.6,  status: convention}
  m_min_members:    {symbol: "m", value: null, status: simulated, source_run: null}
  delta:            {symbol: "δ", value: null, status: fitted,    source_run: null}

Freeze protocol

  1. viveka registry validate checks schemas, cross-references (every prompt names a schema; every filter list names a commitment) and that no fitted value is null.
  2. viveka registry freeze --reason "…" computes SHA-256 over every file under registry/ except FROZEN.json, writes the manifest, appends a change-ledger entry, commits, and creates the git tag registry-v<N>.
  3. Optionally, the manifest hash is deposited with an external timestamp (decision D-5). The git tag alone is a guardrail against accident, not proof against a determined rewrite.
  4. Every stage must call registry.verify() at start: recompute the hashes and refuse to run if they differ from FROZEN.json, unless the stage is explicitly a development-fold stage run against a draft.

Version rules

  • Any change after freezing is made by viveka registry bump, which copies the frozen version to a draft, records the reason and the result that prompted it, and requires a new freeze.
  • Contested cases scored under an earlier version are marked superseded and re-registered, never rescored in place, as the framework requires.
  • Parts of the registry freeze at different times: thresholds after calibration, filter lists after S5 for each commitment, redaction after S6. FROZEN.json therefore records a hash per component, and each stage verifies only the components it depends on plus everything upstream of them.

Ordering constraints the code enforces

  • No stance before eligibility. S8 refuses to run for a case whose S4 report is missing or failed. This implements "a pair that could not have been separated is replaced before the test".
  • No coding before audits. S8 codes only with coders marked qualified by the latest S7 report for that registry version.
  • No scoring before predictions are frozen. S10 refuses to score a pilot or contested case unless registry/predictions/ for that case is in the frozen manifest with a timestamp earlier than every S8 run for the case.
  • Census before calibration. S12 computes trigger 1 only over fields that passed S2, and records replaced fields.
  • Development folds are isolated. Codebook, filter wording and fitted thresholds may be developed only on runs tagged fold=dev; a held-out field's data path is not readable by development runs.
8 · Coders

The coder subsystem

Coders are the framework's most exposed component, so this subsystem carries the most rules. Everything here implements the framework's section "Coders are instruments".

Interface

class Coder(Protocol):
    coder_id: str          # e.g. "anthropic:claude-opus-5", "human:rater-02"
    family: str            # independence unit: "anthropic", "human:rater-02", ...
    def submit(self, task: TaskSpec, items: list[Item]) -> SubmissionRef: ...
    def collect(self, ref: SubmissionRef) -> list[RawOutput]: ...   # archived verbatim first
    def parse(self, raw: RawOutput, schema: dict) -> Label | Missing: ...

Intervals resample over family, never over coder_id or repetitions. Two Claude models, or one model with several prompts, are one family (H4).

Every task has a prompt in registry/prompts/ and a JSON Schema in registry/schemas/. The prompt embeds the relevant codebook section verbatim, so a codebook change changes the prompt hash and therefore the task version.

Automated coder: Anthropic adapter

  • Endpoint. Message Batches API (client.messages.batches.create), which accepts up to 100,000 requests or 256 MB per batch, usually completes within an hour and at most within 24, and costs half the standard rate.
  • Model. The exact model ID is a registry value. The default is claude-opus-5; choosing a cheaper model trades measurement quality for cost and is decision D-4. IDs are used exactly as listed by the Models API, without date suffixes.
  • Output. Structured outputs via output_config: {"format": {"type": "json_schema", "schema": …}}, with effort set in the same object from the registry. The schema is the registered one; the parser still validates every result and records a failure as Missing, never as a guessed label.
  • Sampling. Claude Opus 5 does not accept temperature, so outputs are not deterministic. Reproducibility therefore rests on archiving raw outputs, and variability is measured: S7 runs a test–retest repetition on the anchor set, and the symmetry audit subtracts that rate as the framework specifies.
  • Caching. The system prompt (task instructions and codebook excerpt) is byte-stable and marked for prompt caching; the item is the only varying content.
  • Request identity. custom_id is a hash of (task_version, item_id, coder_id, rep). Results arrive in any order and are joined only by custom_id.
  • Retention. Batch results stay retrievable for 29 days. The collector downloads every result to data/raw/coders/<run_id>/results.jsonl immediately after the batch ends, before parsing, and records the batch ID in the run manifest.
  • Refusals and errors. A result with stop_reason: "refusal" is stored as Missing(refusal) with its category. errored and expired results are resubmitted once, with the same custom_id and a logged retry; persistent failures stay missing. The share of missing labels per case and side is reported, because missingness that differs by side is itself an asymmetry.

No server-side model fallback

The API can reroute a refused request to another model. The harness must not enable this: a label silently produced by a different model breaks the coder's identity and the one-family rule. A refusal is recorded as missing instead.

Human coders

  • viveka packets export --task T1 --rater rater-02 writes a spreadsheet packet of redacted items in randomised order, with no identifiers beyond an opaque item key.
  • viveka packets import validates every row against the task schema and stores the file verbatim in data/raw/coders/.
  • Recruitment, training and number of human coders are decision D-3. The framework requires at least one human in every pool.

Second model family

The framework bars any model family used in developing it from being the only automated coder. Because this framework was developed with Claude, an automated pool needs either a second, non-Claude model family or a second human coder. The adapter follows the same interface; the provider is decision D-2.

Model retirement

A retired model cannot be rerun. Its archived outputs remain valid for the registry version that used it. Replacing it means registering a new coder, re-auditing, and bumping the registry version; labels from the two coders are never pooled as one.

9 · Verdict engine

Measures and the four gates

The engine is a pure function: verdict(measures, registry) → Verdict. It performs no I/O, reads no clock and draws no randomness except through a seeded generator passed in. It is built and tested before any real data exists (H5).

Measures (viveka.measures)

  • Favoured side. For each lineage and window, the side its citations support on balance: support citations to results for a side, plus discount-only citations of results against it. Computed first; every other measure is oriented to it.
  • Δ. For each frozen filter, the rate at which the cluster invokes it (T1 reason spans mapped to filters) against unfavourable results to which T3 says it applies, minus the same rate for favourable results; combined over filters weighted by applicable results. Invocations of filters marked uncheckable count wholly as asymmetric.
  • Ω. Among results bearing on the claim, stratified by prominence quantile, the share of favourable results the cluster cites minus the share of unfavourable results; averaged over strata.
  • Ledger statistics. Insulating share (C and D codes, including rounds closed as C) and loop length L, computed on the favoured side's disconfirmations.
  • τ, H, χ. As defined in the framework; τ counts only breaks backed by evidence no frozen filter excludes, and χ is computed but never passed to the gates.

Intervals

Every interval is a percentile bootstrap at the registered level, resampling evidence items within the window and coder families jointly; L is recomputed on each resampled ledger. Where the anchored disagreement (§8) exceeds the disagreement observed in the case, the coder resampling uses a noise model calibrated to the anchor set instead. The number of bootstrap draws and the seed are recorded in the run manifest.

Gates (viveka.verdict.gates)

def verdict(m: Measures, reg: Registry) -> Verdict:
    if m.trajectory_closed:                                  return Verdict.CLOSED
    if not m.cites_observation:                              return Verdict.OUT_OF_SCOPE
    # gate 1 · eligibility
    if (m.n_disconfirmations < reg.n or m.members < reg.m
            or m.citations_on_claim < reg.v or m.coverage < reg.r):
        return indeterminate(Reason.INSUFFICIENT_DATA)
    # gate 2 · primary reading (intervals already oriented to the favoured side)
    reading = primary_reading(m.delta, m.omega, m.insulating_share, m.loop_length, reg)
    if reading is Reading.UNCLEAR:
        return indeterminate(Reason.READING_UNCLEAR, note=reading.note)   # incl. "points away from favoured side"
    # gate 3 · conduct check
    for measure in (m.tau, m.honoured):
        if measure.measurable and measure.points_against(reading):
            return indeterminate(Reason.CONDUCT_CONFLICT)
    # gate 4 is applied across runs by S11, not here
    return Verdict.HEALTHY if reading is Reading.S else Verdict.INSULATED

primary_reading returns S if both the Δ and Ω intervals lie inside ±δ and the insulating-share interval lies wholly below c; A if either interval lies wholly beyond δ toward the favoured side and the L interval lies wholly at or above k; otherwise UNCLEAR with a note naming the combination.

Stability (stage S11)

S11 reruns S3 to S10 over the Cartesian product of registered resolutions, clustering methods, o values and window variants, joins verdicts on lineage identity, and keeps a verdict only if identical in every run; otherwise indeterminate · unstable. Lineage identity across partition variants is matched by maximum membership overlap; unmatched lineages count as instability.

Field summaries and triggers (stage S12)

  • Field summaries follow the framework: lineages descending from the community where the claim was first tested; split when one lineage is healthy and another insulated, in any windows.
  • Triggers 1 to 6 are computed as named functions, each returning a status, the numbers behind it, and the verdicts it used. Trigger status is reported and appended to the change ledger; the harness never acts on a trigger by itself.
10 · Simulator

Synthetic communities

The simulator exists so that the verdict engine can be tested, and the framework's simulated parameters set, before any real case is touched.

Generative model

  1. Social layer. A degree-corrected stochastic block model with planted clusters, evolving over yearly steps with membership churn, splits and merges, so lineage tracking is exercised.
  2. Evidence. A stream of results for and against a claim, each with methods properties (which filters apply) drawn independently of direction, and a prominence value.
  3. Behaviour. Each planted cluster has a behaviour profile: symmetric (filters applied to both sides; citation independent of direction), filter-asymmetric, omission-asymmetric, or both, with tunable strength; plus ledger response probabilities for A–D and round outcomes.
  4. Coders. Labels are passed through per-family confusion matrices; once S7 has run, those matrices are the measured ones.

Not yet a framework rule

Setting δ, c, k, t and h from simulated symmetric communities, rather than fitting them on calibration fields, was proposed but has not been adopted by the framework document. The simulator supports it; the registry keeps those parameters as fitted until the framework says otherwise (decision D-7).

11 · Claude Code configuration

How the agent is constrained

Three mechanisms, in order of strength: permission rules (enforced before a tool runs), hooks (scripts that inspect each call and can block it), and project instructions (read every session). None of them is a security boundary against a determined user; the hash manifest and git tags are the real record (§5, §12).

CLAUDE.md (project rules)

# Viveka

Framework: docs/evidence-that-cuts-both-ways.html. Harness spec: docs/viveka-harness-spec.html.

## Non-negotiable
- Never produce, edit or "fix" a label, measure or verdict by hand or in conversation.
  They come only from `viveka` stages. If output looks wrong, find the bug in code.
- Never edit files listed in registry/FROZEN.json. Propose a version bump instead
  (`/log-decision`, then `viveka registry bump`).
- Never read registry/predictions/ while working on coding prompts, filters or redaction.
- Never overwrite anything under data/raw/ or runs/.
- Never run a stage that spends money without the user's explicit go-ahead in this session.
- Any change to registry/ drafts, prompts or the codebook needs a reason in the change ledger.

## Working
- Python via uv: `uv run pytest`, `uv run viveka <stage>`.
- The verdict engine and simulator must stay pure and fully tested.
- Where the framework document is ambiguous, stop and record a decision; don't improvise.

  • Derived tables are written under a path containing their content hash; a run never overwrites a previous output (H3).
  • viveka verify <run_id> recomputes every hash, and re-parses raw coder outputs to confirm the stored labels.
  • viveka rederive <verdict_id> rebuilds a verdict from archived labels and the recorded registry version, and must reproduce it exactly given the recorded seed.
  • A run with git_dirty: true may be used for development folds only; S10–S12 refuse it for pilot, held-out or contested cases.
13 · Cost

Spend controls

Coding is the only stage with material API cost. The harness makes every paid run deliberate and accounted for.

  • Estimate before running. --dry-run renders the requests, counts input tokens on a sample with the token-counting endpoint, projects output tokens from the anchor-set runs, and prints the estimated cost using prices read from configuration, not hard-coded.
  • Confirm explicitly. Paid stages refuse to start without --confirm-spend <estimate> matching the dry-run figure within a tolerance; /run-stage is user-only.
  • Budget ceiling. instrument.yaml holds a project budget and a per-run cap (decision D-6); the pipeline refuses a run that would exceed either, based on usage recorded in manifests.
  • Levers, in order. Batch pricing and prompt caching of the stable system prompt are built in. Model choice, effort level and the number of repetitions affect measurement quality and are registry decisions, not optimisations the harness makes on its own.
  • Pilot first. Coding runs on the anchor set and one pilot case before any calibration field, so real per-item costs replace estimates early.
