Viveka Harness Specification

How the framework in Evidence That Cuts Both Ways is built and run as a research harness: Claude Code builds and operates a deterministic, versioned pipeline, and every measurement comes from registered instruments whose outputs are archived and auditable.

Implements Evidence That Cuts Both Ways (revision of 14 September 2026) · companion to The Insulated Core
Harness principles6 clauses · every requirement below traces to one
H1

Engineer, not instrument

Claude Code writes, runs and maintains the pipeline. No label, measure or verdict is ever produced inside an agent session; they come only from versioned pipeline code and registered coders.

H2

Frozen before seen

Every threshold, rubric, prompt, query and event list is frozen by content hash before the data it governs is coded or scored. A change after freezing is a new registry version.

H3

Provenance on everything

Every artefact records the registry hash, code commit, inputs and coder that produced it. Raw coder output is archived before it is parsed.

H4

Instruments held to P

Coders pass the leakage test, the symmetry audit and the agreement threshold before their labels count. One model family is one coder.

H5

Deterministic core

The verdict procedure is a pure function of measures and registry, tested on synthetic data before it ever sees a real case.

H6

Revisions are debited

Every change to the codebook, prompts or parameters is appended to a change ledger with the result that prompted it. Nothing is edited silently.

1 · Scope

What the harness does, and what it does not

The harness turns the framework into a runnable study: it assembles corpora, builds the social and epistemic layers, codes evidence under the coder rules, computes the measures with their intervals, applies the four-gate verdict procedure, and checks the framework against its own revision triggers.

In scope

  • The pilot (fifth force against cold fusion), its reserve pair, and the calibration fields named in the framework.
  • Every instrument in the framework: the Anomaly Response Ledger (codes A–D, rounds), Δ read reason by reason, Ω, H, τ, χ, and the independent checks (depth ratio, deletion).
  • The registry, its freeze and versioning protocol, and the change ledger.
  • The coder subsystem: automated coders through batch APIs, human coders through exported packets, and the audits every coder must pass.
  • The simulator that sets m and v and checks whether the pilot can separate its cases at all.
  • Claude Code configuration: project instructions, permissions, hooks, subagents and skills.

Out of scope

  • A user interface beyond generated HTML reports.
  • Scoring contested cases (psychoanalysis, string theory and the rest). The harness supports them, but none is scored until calibration and the pilot have passed.
  • Acquiring any literature by circumventing paywalls, access controls or a source's terms.
  • Changing the framework. Where building exposes a gap in the framework, the harness records it as a decision for the framework document (§17), not a local workaround.

Normative language

must marks a requirement the build is checked against. decision marks a choice that belongs to the project owner and is listed in §17. Parameter values quoted here are the framework's proposed values; the registry, not this document, is authoritative once frozen.

Blocking gap: no Linux runtime

The framework requires community detection by at least two methods, one of them a hierarchical stochastic block model. The reference implementation, graph-tool, does not run natively on Windows; GROBID, used to extract citation contexts from PDFs, is distributed as a Java service normally run in Docker. Until a Linux runtime exists (WSL2, Docker Desktop, or a remote Linux runner), stage S3 can run Leiden clustering only, and every verdict computed without the second method must be marked provisional and cannot pass gate 4. Installing WSL2 changes system settings and is left to the project owner.

Credentials

  • ANTHROPIC_API_KEY for automated coders (§8).
  • An OpenAlex API key: required for all API calls since 13 February 2026, with usage-based credits. Bulk work uses the free CC0 snapshot instead (§14).
  • A Semantic Scholar API key is optional. Without one, the contexts stage uses the public API at a slower registered rate (keyless_requests_per_second); no account is needed.
  • Credentials for the second model family, once chosen (decision D-2).

Credentials live in a git-ignored .env file loaded by the pipeline. Claude Code must be denied read access to it (§11).

3 · Architecture

Four layers, one direction of trust

The layers differ in what they may do. Orchestration may change code but produces no evidence. The pipeline produces evidence but cannot change the registry. The registry governs both and changes only through its versioning protocol.

Why the agent is not an instrument

A Claude Code session is not reproducible, reads the whole repository including the predictions, and has taken part in developing the framework. Any of those disqualifies it as a coder under the framework's own rules. Automated coding therefore runs through fixed prompts sent by pipeline code to a pinned model through the Message Batches API, with outputs archived; the agent builds that code but never stands in for it.

5 · Registry

Registry, freezing and versions

The registry is the framework's "fixed before scoring" made mechanical. The pipeline reads it; nothing writes to a frozen version.

Contents

Thresholds and conventions from the framework's parameter registry live in thresholds.yaml, each with its value, its status (fitted, simulated, convention) and, for fitted and simulated values, the run that produced it. Instrument components from the framework's second registry table live in the other directories. The loader (viveka.registry.thresholds) rejects a thresholds file that lacks any parameter in its PARAMETERS list, and raises when code reads a value that is still null; a test keeps PARAMETERS identical to the schema's required list.

Freeze protocol

  1. viveka registry validate [component…] checks syntax, the JSON Schemas, orphan files and cross-references: a prompt's front matter names an existing schema, a filter list names a claim with an events file, and every source_run has a run manifest. Events and cases have registered formats (JSON Schemas events and cases, format 1) from M4a, and a case must name a claim with an events file; calibration fields have format 1 of schema fields from M4b, and a frame may ingest only venues registered in corpus; formats for filters, predictions and redaction arrive with their milestones, and until then those files need only be YAML mappings with a format key.
  2. viveka registry freeze <component…> --reason "…" refuses unless validation passes and: no thresholds value is null; every fitted or simulated value has a source_run; each component has files and differs from what is already frozen; every upstream component is frozen or frozen in the same call; already-frozen components still verify; and the tag is free. It then writes the manifest atomically, appends a freeze record to the change ledger, commits exactly the newly frozen files, the manifest and the ledger (a pathspec commit that leaves other staged work alone), and creates the annotated tag registry-v<N>. --no-git exists for development and tests only.
  3. Optionally, the manifest hash is deposited with an external timestamp (decision D-5). The git tag alone is a guardrail against accident, not proof against a determined rewrite.
  4. Every stage runs inside RunContext (§12), which calls require_frozen(components, fold): it verifies the named components and everything upstream of them, refuses drafts outside the development fold, and refuses a frozen component whose files no longer match in every fold, including development.

Version rules

  • Any change after freezing is made by viveka registry bump <component…> --reason "…" --prompted-by "<run or result>". It returns the components, and every frozen component downstream of them, to draft; appends a bump record holding their old hashes, the cascade, the reason and what prompted it; and requires a new freeze. It refuses to bump a component whose frozen files have already been changed: restore them from the tag first. The old version stays retrievable at its registry-v<N> tag.
  • Contested cases scored under an earlier version are marked superseded and re-registered, never rescored in place, as the framework requires (built with scoring, M9).
  • Parts of the registry freeze at different times: thresholds after calibration, filter lists after S5 for each commitment, redaction after S6. FROZEN.json therefore records a hash per component, version rises by one on every freeze, and each component keeps the frozen_in version of the freeze that included it.

Ordering constraints the code enforces

  • No stance before eligibility. S8 refuses to run for a case whose S4 report is missing or failed. This implements "a pair that could not have been separated is replaced before the test".
  • No coding before audits. S8 codes only with coders marked qualified by the latest S7 report for that registry version.
  • No scoring before predictions are frozen. S10 refuses to score a pilot or contested case unless registry/predictions/ for that case is in the frozen manifest with a timestamp earlier than every S8 run for the case.
  • Census before calibration. S12 computes trigger 1 only over fields that passed S2, and records replaced fields.
  • Development folds are isolated. Codebook, filter wording and fitted thresholds may be developed only on runs tagged fold=dev; a held-out field's data path is not readable by development runs.
  • No census without a corpus. S2 refuses unless a successful S1 run exists for the same case, fold and registry component hashes.

Interpretations fixed in M4a

  • Frames before clusters. The framework takes the census per cluster, but clusters arrive at S3 (M5). Until then the census unit is a registered frame: the works citing a case's seed works, or the works in its community venues. M5 reruns the same census code with cluster frames, as stage S2C (viveka census --clusters): one frame is one lineage's cluster in one sub-window, holding the papers its members published in that sub-window, and the sample inside a frame is the registered seeded draw, unchanged. S2C runs after S4, because gate 1's first two checks decide which literatures are worth measuring: only the lineage-windows that meet m and v and are not closed are framed, since coverage can withhold eligibility but never grant it. S4 then reruns and reads each window's coverage from its own cluster frame, at the resolution S2C censused; the sweep's other resolutions keep coverage unmeasured until their own S2C run. A separate stage id keeps latest_run lookups of the frame census (S2) unambiguous.
  • The census reports; gate 1 judges. S2 records coverage per frame and publication year and never compares it with r. r lives in thresholds, which cannot be frozen until n is fitted (M8), and a strict-fold run needs every component it uses frozen; S4 applies r per sub-window.
  • Denominators from Crossref. OpenAlex's referenced_works lists only references it matched, so it cannot give the share that failed to resolve. A sampled work's reference list comes from Crossref (open since June 2022) or a manual import. A reference with a deposited or Crossref-matched DOI resolves when the DOI is in OpenAlex. The first dev-fold census (16 Sep 2026) showed that such references resolve 99.7–100% of the time and that 30–44% of all references have no DOI, so a DOI-only rule measured DOI completeness rather than coverage, and penalised community venues most. References without a DOI are therefore matched from a sample: up to doiless_sample_per_work per sampled work, looked up in OpenAlex by year (± match_year_tolerance), volume and first page, with the journal name breaking ties; each frame-year's matched share estimates the rest (resolution: crossref_doi_plus_sampled_biblio_match). References whose year, volume and page cannot be read count as unmatched, and the report gives their share so any understatement is visible.
  • Unmeasured, not guessed. A sampled work with no reference list (typically proceedings, books and scans) is unmeasured. A frame or year whose unmeasured share exceeds max_unmeasured_share is not measurable. The rule is the same for every frame, so poorly indexed literatures are reported as such rather than silently scored low or excluded.
  • Only research papers count (user decision, 16 Sep 2026). Frame works whose OpenAlex type is not in corpus.census.paper_types (article, review, letter, conference-paper) are excluded before sampling. References with a DOI take the type of the work the DOI resolves to. References without a DOI are classified by reference_classification: crossref_fields_v1: a volume title without a journal, report numbers, theses, preprints, unpublished work, web pages, publisher-and-city book citations and news are excluded; series titles and proceedings are kept; references too sparse to classify are excluded and counted separately. A title search of 20 unmatched references found about 5 real papers missed through citation errors, about 9 in journals the corpus does not index, and about 5 that were not papers. OpenAlex's lexical search found none of them; Crossref's query.bibliographic found the right paper for about 5.
  • Recovering miscited papers. A sampled DOI-less paper reference that volume and page do not match is queried once with Crossref's bibliographic matcher (free). A candidate counts only if it is a journal or proceedings article scoring at least bibliographic_rescue.min_score (40), falls within the year tolerance when both years are known, and either shares title_word_share (80%) of its title words with the citation or agrees on volume, first page or journal; its DOI must then be a paper in OpenAlex. Thresholds come from the 20-reference search: correct hits scored 43–90, and a wrong hit scoring 80 (a different paper by the same group) failed the verification. An audit of 15 accepted recoveries under that first rule found 5 false matches, so rule crossref_bibliographic_v2 also rejects a journal article offered for a proceedings citation, a candidate whose volume and page both contradict the citation (unless at least 7 title words match at 85%), titles under five words, and, when the citation carries its own title, a title match that does not hold both ways. The report shows recovered matches in brackets.
  • Tables carry no run id. Parquet tables are content-addressed and named in the run manifest (params.tables), so a run that replays archived responses reproduces them byte for byte; the manifest, not a column, ties a table to its run.

Interpretations fixed in M4b

  • A calibration field is its venues first. The framework scores commitments but folds by field, and the census comes before coding. A field (fields/<field>) therefore registers only its side, one window for every field (1986–2025, owner decision 16 Sep 2026) and frames of its community's own venues; its commitments (claims, seeds, events) are drafted and frozen before any M6–M7 coding. A field has no bearing set, so corpus contexts refuses it. A candidate with no indexed venue (astrology) stays on record with no frame and absent venues listed, so the census records it rather than dropping it unseen.
  • Selection before results (decision D-10). A pseudoscience qualifies only if a national scientific body, government review or court has judged its core claim unsupported; a science only as uncontested textbook consensus. A field needs venues of its own; mixed venues are left out; parapsychology and cold fusion are excluded as pilot subjects. Before any calibration census, viveka field overlap measures author overlap between fields and with the cases' community frames: core authors (at least two community works) shared, over the smaller subject's core authors, compared by OpenAlex author id when both subjects are all OpenAlex works and by family name with every initial otherwise (overlap_coefficient_core_v2); above 0.2 the smaller field is dropped. Jaccard was rejected because a small field inside a large one would pass; rule v1, which compared every author by family name and first initial, was replaced after its dev-fold run matched a third of any small field's names to namesakes among immunology's 156,000. Under v2, seismology (25.0% shared with plate tectonics) was dropped and replaced by organic chemistry (18 Sep 2026).
  • Ingested venues (decision D-1). Community venues that OpenAlex does not index are listed from their own archives by registered adapters (CRSQ repository export, Journal of Orthomolecular Medicine contents pages, Answers Research Journal volumes, OJS archives for Subtle Energies & Energy Medicine, BIO-Complexity and the International Journal of High Dilution Research, bepress Digital Commons for the Indian Journal of Research in Homoeopathy) as works X:<venue>:<key> with authors by name. Web pages and PDFs are archived like API responses. Only sampled papers' documents are fetched; references come from PDF text layers or web pages (pypdf_text_v1, reference_section_v2), with no OCR, so a scan without text leaves its paper unmeasured. A document the publisher refuses (HTTP 401 or 403) is not worked around: the refusal is archived so the run replays, its paper is unmeasured, and the report counts refusals per venue. DOI-less references are matched first against the ingested venues' listings (ingested_catalogue_v1: journal alias, volume, year, then first page or first author), since communities cite their own journals. A registered sample of 60 extracted references per census is checked by hand against the documents (viveka corpus audit), and the census report states the verdicts or says the extraction is unaudited. The owner audited orthomolecular medicine (correct 60 of 60); the audits of intelligent design, energy medicine and homeopathy were skipped for lack of access, and creation science's completed sheet was lost, so those censuses are unaudited (D-1 notes, 19 Sep 2026).
  • Venue lists are not tuned on census results. The dev-fold censuses run before the v2 freeze show whether the adapters and extraction work; the venue lists were drafted before them and change only for reasons recorded in the change ledger, never to raise a field's coverage. The counted census is the calibration-fold run under the frozen registry.

Automated coder: Anthropic adapter

  • Endpoint. Message Batches API (client.messages.batches.create), which accepts up to 100,000 requests or 256 MB per batch, usually completes within an hour and at most within 24, and costs half the standard rate.
  • Model. The exact model ID is a registry value. The default is claude-opus-5; choosing a cheaper model trades measurement quality for cost and is decision D-4. IDs are used exactly as listed by the Models API, without date suffixes.
  • Output. Structured outputs via output_config: {"format": {"type": "json_schema", "schema": …}}, with effort set in the same object from the registry. The schema is the registered one; the parser still validates every result and records a failure as Missing, never as a guessed label.
  • Sampling. Claude Opus 5 does not accept temperature, so outputs are not deterministic. Reproducibility therefore rests on archiving raw outputs, and variability is measured: S7 runs a test–retest repetition on the anchor set, and the symmetry audit subtracts that rate as the framework specifies.
  • Caching. The system prompt (task instructions and codebook excerpt) is byte-stable and marked for prompt caching; the item is the only varying content.
  • Request identity. custom_id is a hash of (task_version, item_id, coder_id, rep). Results arrive in any order and are joined only by custom_id.
  • Retention. Batch results stay retrievable for 29 days. The collector downloads every result to data/raw/coders/<run_id>/results.jsonl immediately after the batch ends, before parsing, and records the batch ID in the run manifest.
  • Refusals and errors. A result with stop_reason: "refusal" is stored as Missing(refusal) with its category. errored and expired results are resubmitted once, with the same custom_id and a logged retry; persistent failures stay missing. The share of missing labels per case and side is reported, because missingness that differs by side is itself an asymmetry.

No server-side model fallback

The API can reroute a refused request to another model. The harness must not enable this: a label silently produced by a different model breaks the coder's identity and the one-family rule. A refusal is recorded as missing instead.

9 · Verdict engine

Measures and the four gates

The engine is a pure function: verdict(measures, registry) → Verdict. It performs no I/O, reads no clock and draws no randomness except through a seeded generator passed in. It is built and tested before any real data exists (H5).

Measures (viveka.measures)

  • Favoured side. For each lineage and window, the side its citations support on balance: support citations to results for a side, plus discount-only citations of results against it. Computed first; every other measure is oriented to it.
  • Δ. For each frozen filter, the rate at which the cluster invokes it (T1 reason spans mapped to filters) against unfavourable results to which T3 says it applies, minus the same rate for favourable results; combined over filters weighted by applicable results. Invocations of filters marked uncheckable count wholly as asymmetric.
  • Ω. Among results bearing on the claim, stratified by prominence quantile, the share of favourable results the cluster cites minus the share of unfavourable results; averaged over strata.
  • Ledger statistics. Insulating share (C and D codes, including rounds closed as C) and loop length L, computed on the favoured side's disconfirmations.
  • τ, H, χ. As defined in the framework; τ counts only breaks backed by evidence no frozen filter excludes, and χ is computed but never passed to the gates.

Intervals

Every interval is a percentile bootstrap at the registered level, resampling evidence items within the window and coder families jointly; L is recomputed on each resampled ledger. Where the anchored disagreement (§8) exceeds the disagreement observed in the case, the coder resampling uses a noise model calibrated to the anchor set instead. The number of bootstrap draws and the seed are recorded in the run manifest.

Gates (viveka.verdict.gates)

def verdict(m: Measures, reg: Registry) -> Verdict:
    if m.trajectory_closed:                                  return Verdict.CLOSED
    if not m.cites_observation:                              return Verdict.OUT_OF_SCOPE
    # gate 1 · eligibility
    if (m.n_disconfirmations < reg.n or m.members < reg.m
            or m.citations_on_claim < reg.v or m.coverage < reg.r):
        return indeterminate(Reason.INSUFFICIENT_DATA)
    # gate 2 · primary reading (intervals already oriented to the favoured side)
    reading = primary_reading(m.delta, m.omega, m.insulating_share, m.loop_length, reg)
    if reading is Reading.UNCLEAR:
        return indeterminate(Reason.READING_UNCLEAR, note=reading.note)   # incl. "points away from favoured side"
    # gate 3 · conduct check
    for measure in (m.tau, m.honoured):
        if measure.measurable and measure.points_against(reading):
            return indeterminate(Reason.CONDUCT_CONFLICT)
    # gate 4 is applied across runs by S11, not here
    return Verdict.HEALTHY if reading is Reading.S else Verdict.INSULATED

primary_reading returns S if both the Δ and Ω intervals lie inside ±δ and the insulating-share interval lies wholly below c; A if either interval lies wholly beyond δ toward the favoured side and the L interval lies wholly at or above k; otherwise UNCLEAR with a note naming the combination.

Stability (stage S11)

S11 reruns S3 to S10 over the Cartesian product of registered resolutions, clustering methods, o values and window variants, joins verdicts on lineage identity, and keeps a verdict only if identical in every run; otherwise indeterminate · unstable. Lineage identity across partition variants is matched by maximum membership overlap; unmatched lineages count as instability.

Field summaries and triggers (stage S12)

  • Field summaries follow the framework: lineages descending from the community where the claim was first tested; split when one lineage is healthy and a different one insulated, in any windows; shifted when determinate verdicts disagree only within one lineage; split takes precedence.
  • Triggers 1, 2, 4, 5 and 6 are pure functions, each returning whether it fired (or that it cannot be evaluated), the numbers behind it, and the commitments it used. Trigger 3 returns "not evaluable" until the framework specifies its confound model. Stage S12 appends trigger results to the change ledger; the harness never acts on a trigger by itself.

Interpretations fixed in M2

Where the framework left a computational choice open, the engine implements the reading below. Each is tested, and changing one is a change to the harness, not a tuning step.

  1. Stance labels are relative to the result, so they never depend on orientation. The framework's "+" for a result favouring p and "−" for a result against p both mean the evidence is accepted (SUPPORT); "×" is DISCOUNT with its reason.
  2. Favoured side: the side with more favouring citations (accepted results for it, discounted results against it), using labels aggregated by majority over coder families. An exact tie is BOTH: S must hold on both orientations, and an A reading takes the side its asymmetry points to.
  3. Δ: for each checkable filter, the discount rate among unfavourable results it applies to, minus the rate among favourable results it applies to. These are averaged, weighted by applicable results. A filter absent from one lane is skipped, and cannot_tell is excluded. An uncheckable filter contributes its share of unfavourable cited results with nothing subtracted. With no filters at all Δ = 0; with filters that cannot be compared, Δ is not computable.
  4. Ω: results are ranked by prominence (ties by id) into equal-count strata. Ω is the mean, over strata holding both kinds, of the cited share of favourable results minus that of unfavourable results.
  5. Ledger: only disconfirmations older than the lag count. Final codes follow the rounds rules, the insulating share is (C + D + B→C) ÷ entries, and L is the longest run of insulating entries in date order, broken by an entry at which p was placed at risk. A round naming no tested auxiliary raises until the codebook fixes its rule.
  6. Intervals: percentile bootstrap with B draws. Δ, Ω and the insulating share resample items and coder families jointly. L resamples families only, keeping date order, because resampling entries would destroy the runs it measures. Majority ties are broken by the seeded generator. When the anchored disagreement exceeds the observed disagreement, draws keep every family and flip aggregated labels at the anchored rate.
  7. τ and H: τ is retention after qualifying breaks ÷ retention after baseline changes, measurable with one qualifying break. H is the honoured share, measurable with h₀ met conditions. Each points to A when wholly below its threshold, to S when wholly above, and nowhere when straddling.
  8. χ: computed, not measurable below coverage r, and never passed to the gates. Signature labels wait for the social layer and registered thresholds (§17).
  9. Stability: a verdict stands only if (verdict, reason) is identical in every variant. Lineages are matched by greedy maximum Jaccard overlap, and an unmatched lineage is unstable.
10 · Simulator

Synthetic communities

The simulator exists so that the verdict engine can be tested, and the framework's simulated parameters set, before any real case is touched.

Generative model

  1. Social layer. A degree-corrected stochastic block model with planted clusters, evolving over yearly steps with membership churn, splits and merges, so lineage tracking is exercised.
  2. Evidence. A stream of results for and against a claim, each with methods properties (which filters apply) drawn independently of direction, and a prominence value.
  3. Behaviour. Each planted cluster has a behaviour profile: symmetric (filters applied to both sides; citation independent of direction), filter-asymmetric, omission-asymmetric, or both, with tunable strength; plus ledger response probabilities for A–D and round outcomes.
  4. Coders. Labels are passed through per-family confusion matrices; once S7 has run, those matrices are the measured ones.

Decision D-7, adopted 14 September 2026

δ, c, k, t and h are set by simulation, and calibration tests them. Settings live in the registered simulation component, which is upstream of thresholds. viveka sim thresholds simulates every registered profile at every grid size and replicate. Each replicate's seed is spawned from the registered seed, so the result doesn't depend on the number of worker processes. The command derives every value as the framework's parameter table defines it and records the grid table and derived values as run artefacts. With --write-draft, it writes the values and their source_run into the draft thresholds, recorded as a change and a reason in the ledger; overridden replicates or bootstrap draws are refused.

δ is the larger of its false-insulated edge and the registered equivalence margin δ₀ (delta_margin, convention 0.15). The false-insulated rule alone gave δ ≈ 0, because a symmetric community's Δ interval straddles zero, which would make healthy readings unreachable. The first registered run used a two-sided rule instead, taking δ from the width healthy communities of the largest grid size need to read inside ±δ; its findings review showed that this ties δ to the grid, so that m could only ever equal the largest grid size. The margin replaced it (user decision, 14 Sep 2026), and the run reports the healthy reach at every size for reference.

The same review made disconfirmations and met revision conditions per-member Poisson rates (0.5 and 0.2, matching the earlier fixed 10 and 4 at 20 members) and extended the grid to 640 members. With fixed counts, c and h saturated at 1.0 at every size, and h could then never point to S.

Scope and performance

  • Membership-level social simulation. Lineages are member sets over windows, with churn, branching and closure; that is enough for eligibility, τ, lineage matching, stability and field summaries. The edge-level block-model generator arrives in M5, where community detection needs a graph.
  • Vectorised bootstrap. Stance and applicability aggregation, Δ and Ω run on NumPy arrays (measures/fast.py), and property tests hold them equal to the readable reference definitions. This was about 16× faster on the registered grid: one replicate across it fell from 113 s to 7 s.

13 · Cost

Spend controls

Coding is the only stage with material API cost. The harness makes every paid run deliberate and accounted for.

  • Estimate before running. --dry-run renders the requests, counts input tokens on a sample with the token-counting endpoint, projects output tokens from the anchor-set runs, and prints the estimated cost using prices read from configuration, not hard-coded.
  • Confirm explicitly. Paid stages refuse to start without --confirm-spend <estimate> matching the dry-run figure within a tolerance; /run-stage is user-only.
  • Budget ceiling. instrument.yaml holds a project budget and a per-run cap (decision D-6); the pipeline refuses a run that would exceed either, based on usage recorded in manifests.
  • Levers, in order. Batch pricing and prompt caching of the stable system prompt are built in. Model choice, effort level and the number of repetitions affect measurement quality and are registry decisions, not optimisations the harness makes on its own.
  • Pilot first. Coding runs on the anchor set and one pilot case before any calibration field, so real per-item costs replace estimates early.
  • Data sources (M4a). OpenAlex calls are priced from corpus.api.openalex.prices_usd before each live attempt and refused once today's spend would pass daily_usd_cap (0.80, below the $1 free allowance); the day's spend is logged in data/usage/, so drafting lookups count too. Responses are archived on first retrieval and replayed at no cost. Paid credit needs decision D-6.

Framework items the harness cannot settle

The framework still lists open items that affect the codebook: how to code a B response that names no tested auxiliary, where design-family boundaries fall, how implied reasons are extracted, and how prominence is matched for Ω. Two further gaps surfaced in M2 and are listed in the framework's open items. The four network-signature labels need thresholds before they can be reported, which is needed by M5. Trigger 3's confound model is unspecified, which is needed by M8.
